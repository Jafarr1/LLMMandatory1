# Local Multi-LLM Coding Workflow Evaluation

This repository contains an evaluation of two local multi-LLM coding workflows:

- **Aider + LiteLLM + Ollama**
- **CrewAI + Ollama**

Both approaches were evaluated using the same models and hardware against a small Task Management API defined in `REQUIREMENTS.md`.

The experimental results are stored on separate branches:

- `experiment/aider`
- `experiment/crewai`

The README files on those branches were generated during the experiments and are kept as evaluation artifacts. This README is the setup guide for reproducing the evaluation.

## 1. Prerequisites

The following software is required:

- Git
- Python 3.10
- Ollama
- Docker

Clone the repository:

```bash
git clone https://github.com/Jafarr1/LLMMandatory1.git
cd LLMMandatory1
```

Download the two models:

```bash
ollama pull llama3.2
ollama pull qwen2.5-coder:3b
```

## 2. Start the Local Model Endpoints

Two separate Ollama endpoints are used:

| Endpoint | Model | Role |
| --- | --- | --- |
| `127.0.0.1:11434` | Llama 3.2 | Architecture / planning |
| `127.0.0.1:11435` | Qwen 2.5 Coder 3B | Coding / editing |

Start one Ollama server on port `11434` and another on port `11435`.

**Windows PowerShell:**

```powershell
$env:OLLAMA_HOST="127.0.0.1:11434"
ollama serve
```

```powershell
$env:OLLAMA_HOST="127.0.0.1:11435"
ollama serve
```

**macOS/Linux:**

```bash
OLLAMA_HOST=127.0.0.1:11434 ollama serve
```

```bash
OLLAMA_HOST=127.0.0.1:11435 ollama serve
```

Run each endpoint in a separate terminal.

Both endpoints remain local and do not need to be exposed publicly.

## 3. Toolchain A — Aider + LiteLLM

Switch to the Aider experiment:

```bash
git checkout experiment/aider
```

Create a Python 3.10 virtual environment:

```bash
python3.10 -m venv .venv
```

Activate it:

**Windows PowerShell:**

```powershell
.\.venv\Scripts\Activate.ps1
```

**macOS/Linux:**

```bash
source .venv/bin/activate
```

Install the required tools:

```bash
pip install aider-chat==0.86.2
pip install "litellm[proxy]==1.81.10"
pip install Flask
```

The branch contains `litellm-config.yaml`, which routes the two roles to separate Ollama endpoints:

```yaml
model_list:
  - model_name: architect
    litellm_params:
      model: ollama/llama3.2:latest
      api_base: http://127.0.0.1:11434

  - model_name: editor
    litellm_params:
      model: ollama/qwen2.5-coder:3b
      api_base: http://127.0.0.1:11435
```

Start LiteLLM:

```bash
litellm --config ./litellm-config.yaml --port 4000
```

Configure Aider to communicate with LiteLLM.

**Windows PowerShell:**

```powershell
$env:OPENAI_API_BASE="http://127.0.0.1:4000/v1"
$env:OPENAI_API_KEY="local"
```

**macOS/Linux:**

```bash
export OPENAI_API_BASE="http://127.0.0.1:4000/v1"
export OPENAI_API_KEY="local"
```

Start Aider:

```bash
aider --architect --model openai/architect --editor-model openai/editor
```

The resulting routing is:

```text
Aider Architect → LiteLLM → Llama 3.2 @ 11434
Aider Editor    → LiteLLM → Qwen 2.5 Coder @ 11435
```

The demo workflow was used to produce architecture/planning output, implement the Flask CRUD API, generate tests and documentation, and attempt Docker deployment validation.

The generated application can be started with:

```bash
python app.py
```

The generated tests can be executed with:

```bash
python -m unittest test_app.py -v
```

The evaluation produced six passing tests.

The documentation generated by Aider is available as `README.md` on the `experiment/aider` branch. During deployment validation, the architect produced a suitable Dockerfile proposal, but the editor failed to create the file successfully. This failure is retained as part of the evaluation.

## 4. Toolchain B — CrewAI

Switch to the CrewAI experiment:

```bash
git checkout experiment/crewai
```

Create a Python 3.10 virtual environment:

```bash
python3.10 -m venv .venv
```

Activate it:

**Windows PowerShell:**

```powershell
.\.venv\Scripts\Activate.ps1
```

**macOS/Linux:**

```bash
source .venv/bin/activate
```

Install CrewAI:

```bash
pip install crewai==1.15.23
```

The branch contains `llm_config.py`, which connects CrewAI directly to the two Ollama endpoints:

```python
from crewai import LLM

architect_llm = LLM(
    model="ollama/llama3.2",
    base_url="http://127.0.0.1:11434"
)

coder_llm = LLM(
    model="ollama/qwen2.5-coder:3b",
    base_url="http://127.0.0.1:11435"
)
```

The CrewAI workflow uses separate responsibilities for:

- Architect
- Tech Lead
- Coder A
- Coder B
- QA
- Documentation
- Deployment

The demo workflow produces architecture and planning output, partitions implementation between coding roles, generates tests and a QA report, creates documentation, and performs deployment validation.

The generated artifacts, including `app.py`, `test_app.py`, `QA_REPORT.md`, `README.md`, and `Dockerfile`, are available on the `experiment/crewai` branch.

## 5. Demo Workflow

Both toolchains were evaluated using the same general workflow:

```text
Architecture
    ↓
Technical planning
    ↓
Implementation
    ↓
Testing / QA
    ↓
Documentation
    ↓
Deployment validation
```

The demo application is a simple Flask Task Management API with the following endpoints:

```text
POST   /tasks
GET    /tasks
GET    /tasks/<id>
PUT    /tasks/<id>
DELETE /tasks/<id>
```

The application uses in-memory storage to keep the evaluation focused on the multi-LLM workflow rather than application complexity.

## 6. Evaluation Artifacts

The two branches preserve the outputs produced during each evaluation:

```text
experiment/aider
experiment/crewai
```

Git was used throughout the experiments to review generated changes, preserve successful artifacts, and recover from unwanted changes.

LLM output is nondeterministic, so repeating the workflow may not produce identical text or code. However, the same endpoints, models, role configuration and workflow stages can be used to reproduce a comparable evaluation.

Some generated artifacts contain errors or incomplete results. These have intentionally been retained because failure handling and reliability are part of the toolchain evaluation.

The full comparison, tradeoffs, failure modes and recommendation are discussed in the accompanying synopsis.
